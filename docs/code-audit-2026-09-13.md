## 一、结论

**项目能够启动，主要视图能够首次渲染，但尚不适合按“完整可靠的拆书工具、门禁全部证明正确”的口径验收。**

发现 **16 项问题：P1 高优先级 4 项，P2 中优先级 10 项，P3 低优先级 2 项**。本次未确认 P0 紧急安全事件；这不等于完成了第三方依赖或线上部署安全认证。

核心风险不是缺少框架，而是三个契约没有闭合：

- 用户以为笔记已保存，实际没有持久化或被另一标签页覆盖。
- 数据已在事件表中存在，UI 却沿另一套未填充字段查找，入口和回链失效。
- 生成、合并、同步与校验对同一数据的理解不一致，既可能覆盖已整理内容，也可能把漏改和错误引用报告为成功。

建议先修复 P1，再处理笔记可靠性、地图重复初始化和校验盲区，暂缓继续扩大数据量。

## 二、详细发现

### F01 · P1：重生成脚本会覆盖已完成的数据整理

**位置**

- `scripts/build_chapters.py:21,100-102,133-158`
- `scripts/build_characters.py:242-258,272-284`
- `README.md:110-122`

**根因与影响**

章节生成器从 `data/chapter_notes.py` 读取人工稿；该来源当前不存在，真实稿件来自 `data/proposals/notes_*.py`。缺稿时返回空表，随后无条件覆盖 `chapters.js`，且序列化时硬写 `event:null`。人物生成器只从内置 58 人 ROSTER 重写 `characters.js`，没有保留已合入的 139 位简录和人工修订索引。

README 把两条命令放在正常数据管线步骤中，未明确其会重置现有成果。提案中保留的部分文本可以重新合并恢复，但只存在于产物中的修订没有这种保障；不能把它们当作安全的日常更新命令。

**实测**：加载原 Python 脚本，仅把 `OUT` 改为临时路径，调用原 `main()`：

```text
build_chapters.py:   361 张章节卡，非空 gist = 0
build_characters.py: 58 位人物，minor = 0
当前正式数据:        361 个非空 gist，197 人物，其中 minor = 139
```

**建议**：初始化骨架与更新现有数据分开；已有产物默认拒绝覆盖。确定人工稿的唯一来源，生成前报告将删除/回退的记录，采用临时输出＋校验＋原子替换。不要仅靠事后重新 merge 掩盖回退风险。

**验收**：对当前产物执行正常更新时，已校订字段不回退、197 位人物不减少；显式重建也必须能从规范来源恢复同等内容。

### F02 · P1：自动保存承诺与实现不符，用户输入会丢失

**位置**：`js/notes.js:18-49`；`js/app.js:62,123,192,357`；`README.md:47`。

人物卡、事件卡占位文案及引导都宣称自动保存，但 `oninput` 只把状态改为“未保存…”，真正写入只发生在点击“保存笔记”后。关闭弹层、打开另一张卡片没有保存或未保存警告。

**浏览器步骤与结果**：打开皮埃尔人物卡 → 输入 `AUDIT_UNSAVED_NOTE` → Escape 关闭 → 重新打开：

```text
placeholder = 记下你的想法…（自动保存在本机浏览器）
重新打开的 textarea = ""
localStorage[wp_notes_v1] = null
```

**建议**：实现与文案一致的保存机制，并在关闭/切换前处理待保存状态；若产品选择手动保存，必须同步改文案并拦截未保存退出。验收覆盖关闭、切换卡片、刷新及存储失败。

### F03 · P1：事件修订脚本对行内字段静默失效

**位置**：`scripts/sync_event_summaries.py:28-30,91-101`。

字段匹配正则以 `^\s*字段名:` 开头，仅接受行首字段。实际事件数据把 `title`、`year`、`month`、`place`、`chars`、`arc`、`flag` 等放在行内；匹配失败直接跳过。脚本可能报告“已更新”，但只更新了其中一部分字段。

**临时副本实验**：给 `e-sherer-saloon` 的提案同时指定：

```json
{"title":"AUDIT_TITLE","chars":[],"year":1810,"summary":"AUDIT_SUMMARY"}
```

执行原同步实现后：

```text
日志：覆盖 summary；共 1 条被更新
实际 title = 舍勒沙龙的晚会       // 未改
实际 year  = 1805                 // 未改
实际 chars = 原来的 7 人          // 未改
实际 summary = AUDIT_SUMMARY      // 已改
```

**建议**：按结构解析记录、按字段更新后统一序列化，不让业务行为依赖换行排版；显式要求更新却未匹配的字段应报错。增加“一次修订多个字段”和“带转义引号文本”的回归场景。

### F04 · P1：全部章节事件入口和事件章节详情回链失效

**位置**：`js/app.js:145,186-188,228,252-253,298`；`data/chapters.js:5` 起；`data/events.js:5` 起。

事件真实关联在 `EVENTS[].ch`，UI 却只读 `CHAPTERS[].event`；当前 361 张章节卡的 `event` 全为空。因此：

- 章节详情不显示“升级为事件”入口。
- 事件详情不显示带概述的“对应章节”列表（顶部原始章节 ID 仍显示）。
- 阅读列表不会出现 `is-event` 标记。

**全量查询**：133 个事件、通过 `CHAPTERS[].event` 指向的事件数 **0**，没有这种回链的事件数 **133**。浏览器打开 `1-1-01`，没有事件入口；通过 `#e-sherer-saloon` 打开晚会事件，也没有“对应章节”区块。

**建议**：以现有 `EVENTS[].ch` 建立章节→事件数组的反向索引；一章可能对应多个事件，不应强制压成单个 ID。显示、导航和校验共用同一来源。验收应覆盖一章多事件、事件多章节及无事件章节。

### F05 · P2：导入不校验 schema，异常文本导致导出界面不可用

**位置**：`js/notes.js:142-149,108-114`。

导入仅检查 `incoming[k].text` 是否真值，不检查字符串、时间戳、键格式及版本。导出预览却无条件调用 `.text.slice()`。

**实际导入文件**：

```json
{"version":1,"notes":{"char:pierre":{"text":123,"at":0}}}
```

浏览器提示“已导入 1 条笔记。”并保存该数值。再点“导出全部”，弹层仍停留在人物卡；执行同一导出实现捕获：

```text
notes[k].text.slice is not a function
```

**建议**：导入前完整验证记录类型、支持的版本和键命名；先验证整批再提交，不接受原型相关键。加载本地历史数据也需校验；异常记录不能使全部备份入口失效。此处已证实的是本地数据污染/可用性问题，未证实远程代码执行。

### F06 · P2：持久化失败时清空和导入仍显示成功

**位置**：`js/notes.js:12-15,38-42,148-150`。

`persistNotes()` 返回失败，但清空和导入分支忽略返回值。普通非空保存虽然会提示失败，也已经先修改内存。

**失败注入**：让存储的 `setItem()` 抛出 `QuotaExceededError`，执行原实现：

```text
清空：noteStatus = 已清空
导入有效字符串笔记：alert = 已导入 1 条笔记。
```

实际上磁盘状态未改变，刷新可能恢复旧记录或丢失刚导入内容。

**建议**：统一提交事务，持久化成功后才更新成功状态；失败保留可导出的草稿及准确提示，不能声称已清空/已导入。验收覆盖配额满、禁用存储与失败后的刷新。

### F07 · P2：多标签页以过期快照整表覆盖

**位置**：`js/notes.js:7-16,33-45`。

每页仅启动时读取一次笔记，保存时覆盖整个 `wp_notes_v1`，没有读取最新版本或同步其他标签页变动。

**原实现双实例实验**：A、B 同时读空存储；A 保存皮埃尔笔记；B 保存安德烈笔记。最终存储只剩：

```json
{"char:andrei":{"text":"B","at":"本次保存时间"}}
```

A 已成功保存的皮埃尔笔记被 B 的旧快照覆盖。

**建议**：至少在提交时合并最新记录并监听 `storage` 事件；明确同一记录冲突策略。若要求强事务保证，可采用事务式存储。验收分别覆盖不同笔记和同一笔记并发编辑。

### F08 · P2：地图二次进入触发重复初始化异常

**位置**：`js/app.js:52`；`js/map.js:16-24`。

每次进入地图都调用 `MapView.init()`，内部没有 `map` 已存在检查，再次对同一个容器执行 `L.map()`。

**浏览器步骤**：地图 → 阅读 → 地图。捕获错误；在同一实际页面直接捕获初始化异常，消息为：

```text
Map container is already initialized.
```

首次地图可以正常显示，不能据此判定重复导航正确；异常也使本次路由后续 `resize()` 调用被跳过。

**建议**：地图初始化幂等，后续进入只调整尺寸；另设明确销毁路径，避免重复监听器和动画残留。验收反复切换并检查错误日志与地图交互。

### F09 · P2：同年共有角色导致事件附上无关战役

**位置**：`js/app.js:144,179-182`。

当前规则是“战役名等于事件地点，或同年共享任意角色”就选第一场战役。共有角色不是战役归属证据，`b.name` 与 `e.place` 也不是同一字段语义。

**浏览器实测**：`#e-sherer-saloon`（舍勒沙龙的晚会）竟显示：

```text
战役阶段 · 申格拉本
```

程序查询还发现家庭、精神转变等事件被同一逻辑挂到会战；不能把所有非 battle 类型一律排除，因为伤亡事件也可能确实属于战役。

**建议**：使用显式战役引用或经核对的映射；未建立关联就不展示。回归用例应包括沙龙不关联战役、战场伤亡正确关联、同年多场战役不取错误的第一条。

### F10 · P2：门禁把泛称命中误报为人物出场证据

**位置**：`scripts/trust_guard.js:88-132,153-170`；`scripts/ctx.py:79-97`。

`LOOSE` 允许“女儿”“妹妹”“伯爵”“大尉”等不绑定身份的词单独证明人物出现，还把 `zhilinsky` 的宽匹配扩展到了其他人物。`ctx.py` 则在整句发现任意人在站/坐等动作时，覆盖转述判定，不判断动作主体是不是查询人物。

**执行原匹配实现的合成反例**（下列为审核自造文本，不是译文）：

| 输入 | 查询人物 | 实际结果 |
|---|---|---|
| 陌生伯爵在花园休息。 | ilya | true |
| 他给女儿寄了信。 | natasha | true |
| 妹妹留在远方。 | marya | true |
| 基莫兴走进营房。 | zhilinsky | true |

另向 `ctx.py` 的临时语料输入“侍女站在门口报告说，远方的玛卡尔病了。”，查询玛卡尔并使用 `--present`，仍输出 `[出场]`。

**影响**：当前 100% 是宽匹配命中率，不是人物身份、正面出场或章节归属的准确率。原脚本也把 kirill 统计为“实际出现 174 章”，显示此统计明显受泛称影响。`ctx.py` 已声明仅作提示，但不能把其标签升级为自动验收证据。

**建议**：分离精确称名、已审定指代和疑似命中；有歧义时待核而非通过。保存人工审定的章节级证据，不用放宽全局正则消除告警。现有索引需重新抽查，但本审核不据此断言全部索引错误。

### F11 · P2：8 处阶段引用悬空，三道门禁未检出

**位置**：`data/relations.js:17-18,27,46,48,55,82,207`；`scripts/lint_data.js:124-149`；`js/relations.js:343-348`。

逐项比对发现 8 处 `phases[].ev` 指向 7 个不存在的事件 ID：

```text
e-marya-icon-blessing
e-marya-godfolk          （引用两次）
e-marya-bourienne
e-bourienne-anatole
e-rostov-money
e-nikolai-sonya-kiss

```

现有 lint、trust_guard、smoke 全部退出 0。关系详情找不到事件时静默省略标题，因此“无控制台错误”也无法发现断链。

**建议**：对每个非空阶段事件引用做全量引用完整性校验，再核实应改 ID、补真实事件还是移除错误引用。不要加入占位事件凑通过。

### F12 · P2：退出码不能可靠表示校验成功

**位置**：`scripts/check_gists.py:75-87`；`scripts/trust_guard.js:47-50`。

- `check_gists.py` 打印问题后没有非零退出逻辑。
- 无 corpus 时 `trust_guard.js` 声称退回弱校验，但没有执行 lint，直接 `exit(0)`。

**隔离最小项目实测**：

```text
check_gists：单条 gist="x" → [结构问题] 1 条 → exit 0
trust_guard：数据不完整且无语料 → 显示弱校验 → exit 0
```

**建议**：结构性错误必须非零退出；人工待核项与明确错误分级处理。弱模式应真正调用结构校验，或明确返回“跳过”，不能把未执行当通过。自动化需要区分通过、失败、缺少前提。

### F13 · P2：1807 年两个人物节点完全重叠

**位置**：`js/relations.js:79-91,176-190,218`。

锚点只计算 1805、1812、1820 年的活动节点。仅在中间年份出现的人物不在任一相关锚点中，`posAt()` 返回 null，渲染统一落到 `[0,0]`。

**执行原图谱实现并捕获 1807 年 ECharts 配置**：

```text
bazdeev   巴兹杰耶夫   x=0, y=0
villarsky 维拉尔斯基   x=0, y=0
```

两个不同人物无法靠当前坐标区分；只验证三个锚点年份会漏掉问题。

**建议**：为全体可能显示节点建立确定性坐标，或为缺失锚点节点提供可区分的位置。验收覆盖全部 1805–1820 年，而非仅锚点。

### F14 · P2：反向人物索引存在，但章节详情隐藏了整段

**位置**：`js/app.js:241-244`。

人物列表实际用 `charsInChapter()`，是否显示该区块却仍用旧 `c.chars.length` 判断。当前受影响章节为 `3-3-30`、`4-1-03`。
